## 1. 一句话结论(本文最值得留下的)

> **"重试之后成功了"只能证明"它有时会失败",不能证明"你刚才那个动作修好了它"。**
>
> 偶发故障里,**第一次成功是最容易让人合上观察的时刻** —— 而那一刻你手里的因果证据是 **0**。

---

## 2. 为什么:一个现场

**现象**:一次 `git push` 报 `fatal: … Failure when receiving data from the peer`,**连失败两次**。
第三次顺手加了个环境变量(`GIT_SSL_CAINFO=/etc/ssl/cert.pem`)→ **成功**。
⇒ 当场结论:「本机 TLS 拦截,推送也吃那把 CA」。该结论被写进项目锚点,**并合并进主干**。

**真相**(同一小时内后续实测,共 5 次):

| # | 带那个环境变量? | 结果 |
|---|---|---|
| 1 | 否 | ❌ `Failure when receiving data from the peer` |
| 2 | 否 | ❌ 同上 |
| 3 | **是** | ✅ **成功** ← **仅凭这一次就下了结论** |
| 4 | **是** | ❌ `Failed sending data to the peer` |
| 5 | 否 | ✅ **成功**(第 1 次就成) |

⇒ 该变量与成败**无因果关系**;**重试本身**才是有效的。

**两处本可免费的证据,全被跳过**:
1. **反例在同一小时内就出现了**(第 4 次带着变量仍然失败)—— 只是结论已成,没人再看;
2. **报错文本本身已经分流了原因** —— `Failure when receiving data from the peer` 是**传输中断**;
   证书问题会报 `SSL certificate problem: unable to get local issuer certificate`。两者形状完全不同。
   把传输中断读成 TLS 配置问题,等于**跳过了手上最便宜的证据**。

## 3. 规则

### B1-R1 · 偶发失败:先重试,再归因;要归因必须有对照

**规则**:面对**偶发**失败,允许先重试(重试是合理的工程动作)。但**不许**把"重试后成功"写成原因。
要把某个动作 X 断言为原因,必须给出**对照**:**带 X / 不带 X 各 ≥2 次**。
拿不出对照,就只能记成「**它偶发失败,重试可过**」—— 这本身就是一条完整的、诚实的结论。

- **反例(实例)**:把「第 3 次带了环境变量就成功」写成「该变量可解此问题」,并据此改写了项目
  锚点的环境说明。第 4 次就出现了「带着变量仍失败」,第 5 次「不带变量成功」。*来源:见 §5。*
- **正例**:同一次事故的收尾写法 —— 「推送偶发失败,报传输中断;**重试 2–3 次**即可;
  与 CA 无因果(实测 5 次:不带 CA 失败-失败-成功,带 CA 成功-失败)」。把**证据表**一起写进去,
  读者能自己判断,而不是只能相信你的结论。

### B1-R2 · 先读错误语义,再开口

**规则**:报错文本通常已经**分了层**。至少先分清这四层,再谈原因:
**① 连接/传输**(reset、broken pipe、receiving/sending data from the peer)·
**② 校验**(证书、签名) · **③ 身份/权限**(401/403、protected branch) · **④ 业务语义**(404/422)。
**跨层归因是最常见的错**,而且成本最低就能避免 —— 你只需要把报错读完。

- **反例(实例)**:`Failure when receiving data from the peer`(①传输层)被归因为"TLS 拦截 CA 不对"(②校验层),
  于是去调一个无效的环境变量;若真问题是代理/网络,这个错结论会**把后续排查引向反方向**。
- **正例**:先按上面四层给报错**归类**,再在**同一层内**找原因。同层内解释不通的,再考虑跨层。

---

### `B1-R3 ⚠️` · 归因前先读「一手证据」,不要从「二手结论」反推

**规则**:先问一句:**「哪个信号能直接区分这两种可能?」** —— 能区分的那一个才叫证据;
其余都是「最常见的可能」,而**最常见的可能,在具体这一次里经常是错的**。
→ 一手证据通常是现成的:**退出码 / 耗时 / 进程状态 / 有无网络连接 / 原始日志 / 字段值本身**。

**反例(实例,同一天、同一人、三次同型错误)**:

① 某用例连续失败,从**合并后的最终结论**(verdict)反推成「判分器误判」——
   而真正的判定来自**确定性层**,报告里 `deterministic.passed=false` **一直就是现成字段**,只是没读它。**连续两轮归错因。**
② CI 某步失败,第一反应是「测试挂了」—— 而**该步耗时 0 秒**已经说明「命令根本没起来」,
   日志后来证实:`file or directory not found:  --cov=eval_gate`(参数被拼坏)。
③ 登录卡住,先猜「浏览器没点授权」—— 而 `lsof` 显示该进程**没有任何网络连接**,
   说明它卡在**本地提示**上(等你按回车),根本没到授权那一步。

*来源:某评测门项目 · 2026-09-12(三次都发生在同一次会话里)。*

**正例**:① 结论**从一手信号出发**,不从「别人给的结论」或「印象里最常见的原因」反推;
② 落到**字段/命令输出**上再开口 —— 说「应该是 X」之前,先指明「哪个证据支持 X」;
③ 与 `A5-R4` 同源(代理指标两端都会错),但更狠一层:那条说「别信启发式」,本条说「**别信你自己的印象**」;
④ 三次同型 ⇒ 这不是偶然,是**默认推理路径的问题**:把「解释现象」当成了「查明原因」。

## 4. 适用场景与不适用场景

**适用**:
- 偶发/间歇性故障(网络、CI、第三方服务、并发相关 flake)的任何**事后归因**;
- 任何"改了一个东西之后就变好了"的**单次观测**;
- 把结论**固化进文档/锚点/团队规范**之前的自查 → 另见 `A1-R16`。

**不适用 / 注意**:
- **确定性复现**的失败不适用本规则 —— 那种情况直接走最小复现即可,不必强求对照;
- **有成本上限时**不必强行做满对照:风险低、代价小的偶发问题,**"重试即可"本身就是最终结论**,
  不必非要找出根因(本实例的最终处置就是如此)。`B1-R1` 只要求:**别把没对照的东西说成原因**。
- **生产事故**里若涉及数据/金钱/对外影响,不能停在"重试即可",必须升级处理 —— 那超出本文范围。

## 6. 怎么验证它被落地

1. **可证伪的自查**:下次遇到偶发失败并准备写下原因时,问自己 ——
   **"我的对照是什么?"** 答不出 → 按 `B1-R1` 降级为"偶发,重试可过"。
2. **一手证据是否在手**:下结论前能否指出**哪个信号**支持它;说不出 ⇒ 按 `B1-R3` 退回取证。
3. **可识别的坏味道**(出现即停手复核):
   - "改了 X 之后就好了"——且只观测到一次;
   - 报错文本与结论**不在同一层**(传输 vs 证书 vs 权限);
   - 结论写成"**可解 / 就是 / 因为**",而证据写成"试了一下,成了"。
