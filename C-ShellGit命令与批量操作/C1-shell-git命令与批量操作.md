## 1. 一句话结论(本文最值得留下的)

> **写代码时的验证纪律,不会自动延伸到"确认工作已完成"的环节。**
>
> 那个环节里没有测试、没有门禁、没人 review —— **唯一的检查就是你随手挑的那个判据**。
> 而随手挑的判据,常常**根本不反映你关心的事**(`A5-R6`),或者**根本没作用于你以为的那些对象**(`C1-R1`)。

**推论**:收尾动作与写码动作**同等对待** —— 每个"我确认过了"的结论,都要能回答"**它错的时候,会变红吗?**"

## 2. 为什么:三个现场(都发生在"我以为已经做完了"之后)

同一轮收尾里连着踩了三个,形状不同、根因同一个:**动作执行了 ≠ 结论成立了**。

| 现场 | 表面 | 实际 |
|---|---|---|
| 判"分支是否已合并" | 用了标准的祖先关系检查,输出整齐 | 该仓库用 **squash merge** ⇒ 判据**结构性失效**,7 个已合并分支全部误报"未合并"(**该条规则见 `A5-R6`**) |
| 批量删分支 | 循环跑了,输出了 7 行结果 | shell **没做单词切分** ⇒ 7 条命令**作用于同一个错误的分支名**,全部失败 |
| 写提交信息 | 内容写好了,命令发出 | 信息里的**反引号**被 shell 当**命令替换**执行 ⇒ 提交**根本没建立** |

三者的共同点:**如果我不看输出、只看"命令返回了",我会认为三件事都成功了。**

## 3. 规则

### C1-R1 · 批量操作:输出必须**逐项可读**;同一错误重复 N 次 = 参数没拆开

**规则**:任何"对 N 个对象做同一件事"的操作,输出必须能分辨**每个对象各自的结果**。
出现**同一行错误重复 N 次**,第一反应是"**参数没有被正确展开**",而不是"N 个对象都失败了"。

- **反例(实例)**:批量删分支时 `for b in $LIST` —— **zsh 默认不对参数展开做单词切分**(与 bash 不同)
  ⇒ 循环只跑一次,`$b` 是整个字符串 ⇒ 7 条命令都在删一个**不存在的分支名**,7 行同样的失败。
  它**没有静默**(每条都打了失败),但错误信息里是**整串名字**,不细看会读成"批量失败"。*来源:见 §5。*
- **正例**:① 用数组/显式列表遍历(`for b in "${ARR[@]}"`),别依赖跨 shell 的切分规则;
  ② **跨方言的写法,先拿 1 个元素试**;
  ③ 输出里带上**每个对象的标识**("已删 X / 失败 X"),让"没拆开"这件事一眼可见;
  ④ 批量删除/覆盖类操作,**先 dry-run 打印将作用的对象列表**,确认对了再执行。

### C1-R2 · 同一坑**第二次**出现 ⇒ 换工具,不是"再注意一次"

**规则**:同一个工具层的坑(引号/转义/shell 方言/编码/路径)在**同一段工作里出现第二次**时,
**停止依赖记性,改掉工具用法**。第二次是最好的信号:它证明"注意一下"对你无效。

- **反例(实例)**:把 Markdown 习惯(反引号 = 行内代码)带进 shell 字符串 ——
  反引号在 shell 里是**命令替换**。第一次(拼 `--body` 参数)靠"改用文件"绕过;
  第二次(拼提交信息)又踩,提交直接语法报错。**两次之间的"注意"没有生效。** *来源:见 §5。*
- **正例**:凡内容含 **反引号 / `$` / `!` / 换行**,**一律不内联** ——
  用 heredoc(`<<'EOF'` 加引号,禁止展开)或写进文件再引用。
  把这条写成**默认动作**,而不是"遇到时想起来"。

### `C1-R3` · 后台任务不要接管道

**规则**:把长任务放到后台跑时,**不要给它接 `| tail` 之类的管道** —— 管道会缓冲,输出不可见,
你只能靠猜它跑到哪了。要么**落文件**(`> log 2>&1`)再 `tail -f`,要么用无缓冲的前台分块运行。

- **反例(实例)**:后台命令接了 `| tail` ⇒ 进度不可见,只能反复猜"它到底在跑吗"。
- **正例**:输出重定向到文件;需要看进度时**另开一条** `tail -f`。

*来源:某评测门项目 · 2026-09-10 · 阶段3 收口。*

### `C1-R4 ⚠️` · CI 某步「0 秒失败」⇒ 先怀疑"命令根本没起来",不是"测试挂了"

**规则**:这是**最快的分诊判据** —— 测试失败要跑完整套(通常十几秒到几分钟),
**0 秒结束**说明命令在**解析/启动阶段**就退出了(参数被拼坏、命令不存在、语法错)。
⇒ 先看**这一步的 `run` 字符串最终是什么**,而不是去读测试输出。

**常见制造者:在 YAML 里手写 shell 续行符 `\`。**

- **反例(实例)**:某 CI 的 `run:` 写成多行、行尾带 `\`。YAML 的 **plain scalar 把换行折成空格,
  而反斜杠是字面量** ⇒ `\ ` 在 shell 里把空格转义 ⇒ `--a=1 --b=2` 被**拼成一个参数**
  ⇒ 命令立刻报用法错误。该步耗时 **0 秒**,而且**掩盖了同一 job 里另一个真失败**
  —— 两个红叠在一起,排查时只顾了一个。
- **正例**:① 多行命令用**块标量**(`run: |`),让换行被保留、`\` 才是真正的续行;
  ② 拿到"0 秒失败"先看**解析后的命令**,别先看日志尾巴;
  ③ 同一 job 里**可能同时存在多个失败**,修掉一个不代表全绿 —— **修完必须重跑看整条链路**。
- **可结构化的守卫(推荐)**:用脚本解析 workflow,断言每步的 `run` **不含 `\ `(反斜杠+空格)**
  —— 那正是"被折行拼坏"的签名。此类守卫要**突变验证**(把 bug 放回去,必须变红)。

*来源:某评测门项目 · 2026-09-12 · 定位"CI 自建立以来一直红"的过程(**两个真因叠加**)。*

## 4. 适用场景与不适用场景

**适用**:
- 任何**收尾/确认**动作:合并了吗?清理干净了吗?推上去了吗?状态对了吗?
- 任何**批量操作**;
- 任何**第二次**遇到同一个工具坑的时刻;
- **写 CI 的多行命令 / 排查 CI 失败** → `C1-R4`;**把长任务丢后台** → `C1-R3`。

**不适用 / 注意**:
- **确定性、可复现的失败**不用本文 —— 直接修即可,不必上升到规则;
- **一次性、无后果的操作**(比如看一眼状态),不必强求双判据;
- 本文**不是**"所有事都要验证两遍"—— 它只要求:**当你声称"已完成"时,你的判据要能反映那件事**。

## 6. 怎么验证它被落地

1. **可证伪的自查句**:说"我确认已完成"之前,问 —— **"这个判据,在那件事没成的时候会变红吗?"**
   答不出(例如"只能看到它说未合并,但它一直这么说")⇒ 换判据。
2. **可识别的坏味道**(出现即停手):
   - 判据输出**全都一样**(全绿 / 全失败 / 全"未合并") —— 先怀疑判据失效,再怀疑对象;
   - 批量操作里**同一行错误重复 N 次**;
   - 你在心里说"注意一下引号/转义"——那是 `C1-R2` 的触发点,不是解决方案。
3. **工具层的最小固化**:把"含特殊字符的内容一律走 heredoc/文件"写成模板或段落,
   让下一次**不需要记得**。
4. **CI 分诊可用**:CI 日志里"某步 0 秒失败"时,能否**立刻**拿到该步解析后的命令?
   (能 ⇒ `C1-R4` 落地;要先翻 YAML 才知道 ⇒ 还没落地)
5. **后台任务可观察**:长任务输出**落文件**、进度可 `tail -f`(而不是接了管道看不见)。
