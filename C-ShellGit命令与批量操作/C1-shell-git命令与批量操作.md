## 0. 怎么用本文(给读取本文的 Agent)

- 你**刚做完一件工作,正在确认"它真的成了"**(合并了吗?删干净了吗?推上去了吗?)→ 先读 `A5` 篇的 **`A5-R6`**。
- 你要**批量操作**(循环删 N 个东西、批量改 N 处)→ 先读 **`C1-R1`**。
- 你**第二次踩到同一个工具坑**(引号 / 转义 / shell 方言 / 编码)→ 直接看 **`C1-R2`**。
- 你要**清一条已经推上去的敏感信息**(邮箱/密钥/内部名)→ 先读 **`C1-R5`**(强推清不干净)。
- 你的 **CI 某一步"0 秒失败"**,或你要在 **YAML 里写多行命令** → 直接看 **`C1-R4`**;
  **跑长任务、要挂 `| tail` 之类的管道** → 看 **`C1-R3`**。
- 你要**用管道判"有没有"或"成没成"**(`if A | grep -q …` / `cmd | tail`)→ **先读 `C1-R6`**。
- 你要跑**破坏性命令**(`reset --hard` / `checkout -- .` / `clean -fd`)→ 先读 **`C1-R1`**。
- 若你踩到了**新的形状**,照 `README.md` **§9(维护流程)** 追加规则;**体例见其 §7**。

## 1. 一句话结论(本文最值得留下的)

> **写代码时的验证纪律,不会自动延伸到"确认工作已完成"的环节。**
>
> 那个环节里没有测试、没有门禁、没人 review —— **唯一的检查就是你随手挑的那个判据**。
> 而随手挑的判据,常常**根本不反映你关心的事**(`A5-R6`),或者**根本没作用于你以为的那些对象**(`C1-R1`)。

**推论**:收尾动作与写码动作**同等对待** —— 每个"我确认过了"的结论,都要能回答"**它错的时候,会变红吗?**"

## 2. 为什么:三个现场(都发生在"我以为已经做完了"之后)

同一轮收尾里连着踩了三个,形状不同、根因同一个:**动作执行了 ≠ 结论成立了**。

| 现场 | 表面 | 实际 |
|---|---|---|
| 判"分支是否已合并" | 用了标准的祖先关系检查,输出整齐 | 该仓库用 **squash merge** ⇒ 判据**结构性失效**,7 个已合并分支全部误报"未合并"(**该条规则见 `A5-R6`**) |
| 批量删分支 | 循环跑了,输出了 7 行结果 | shell **没做单词切分** ⇒ 7 条命令**作用于同一个错误的分支名**,全部失败 |
| 写提交信息 | 内容写好了,命令发出 | 信息里的**反引号**被 shell 当**命令替换**执行 ⇒ 提交**根本没建立** |

三者的共同点:**如果我不看输出、只看"命令返回了",我会认为三件事都成功了。**

## 3. 规则

### C1-R1 · 破坏面不可见的操作:先把作用范围**打印出来**;同一错误重复 N 次 = 参数没拆开

**规则**:任何"**作用范围不由你逐项确认**"的操作,执行前必须**先把作用范围打印出来**、看一遍再动。
这类操作有两种,判据不同:

| 类型 | 例 | 事前该做什么 |
|---|---|---|
| **批量操作**(对 N 个对象做同一件事) | 循环删 N 个 / 批量改 N 处 | **dry-run 打印将作用的对象列表** |
| **破坏性命令**(作用域远超字面意图) | `git reset --hard` / `checkout -- .` / `clean -fd` / `branch -D` | **`git status`** —— 它的损失面是"**全部未提交改动**",**不是**一个能枚举的清单 |

并且:出现**同一行错误重复 N 次**,第一反应是"**参数没有被正确展开**",而不是"N 个对象都失败了"。

- **反例(实例)**:批量删分支时 `for b in $LIST` —— **zsh 默认不对参数展开做单词切分**(与 bash 不同)
  ⇒ 循环只跑一次,`$b` 是整个字符串 ⇒ 7 条命令都在删一个**不存在的分支名**,7 行同样的失败。
  它**没有静默**(每条都打了失败),但错误信息里是**整串名字**,不细看会读成"批量失败"。*来源:见 §5。*
- **反例(实例,同一形状的第二次发作)**:一个「扫本机仓库提交身份」的脚本,首版用 `for x in $LIST` 遍历
  `find` 的输出,而**路径里含空格**(形如 `<某目录>/01.Some Agent`)⇒ 行被拆成词 ⇒ 循环遍历到的是
  **路径碎片**(`Agent`、`Agent_备份…`)⇒ 打出 **8 条一模一样的假告警**,而**真实仓库一个没错**。
  **同批还犯了第二个错(判据不匹配机制)**:把「读不到提交身份」也判成风险 —— 那种仓**提交时会直接报错**,
  不会静默泄露。⇒ 判据要按「**能不能真的造成后果**」分档,而不是「只要不是期望值就报警」。
  *来源:某评测门项目 · 2026-09-12 · 公开仓隐私排查轮(本库自身的运维)。*
- **反例(实例 · 破坏性命令,作用域远超字面意图)**:**为了验证一个性质**,先做了一个"临时提交",
  验完用 `git reset --hard HEAD~1` 回退 ⇒ **`--hard` 的破坏面是【工作区】,不是"那个提交"**
  ⇒ 当天**全部未提交产出**被抹掉。恢复靠的是**悬空提交**(`git reflog`),
  ⚠️ **那是运气**(对象默认有宽限期才没被回收),**不是任何机制**。
  ⚠️ 而且**恢复出来的不是最新态**:临时提交抓的是**索引** ——
  只改了工作区、**没 `git add`** 的那部分改动**没有任何对象可依附** ⇒ **真丢了**,只能靠记忆重贴。
  ⇒ 它同时暴露两条附加判据:**跑之前先 `git status`**;**频繁 `git add`**(索引是最后一道可恢复层)。
  *来源:见 §5。*
- **正例**:① 用数组/显式列表遍历(`for b in "${ARR[@]}"`),别依赖跨 shell 的切分规则;
  ② **跨方言的写法,先拿 1 个元素试**;
  ③ 输出里带上**每个对象的标识**("已删 X / 失败 X"),让"没拆开"这件事一眼可见;
  ④ 批量删除/覆盖类操作,**先 dry-run 打印将作用的对象列表**,确认对了再执行;
  ⑤ **破坏性命令靠的不是 dry-run,是事前的 `git status`** —— 先看清"这条命令跑完,我损失的最大范围是什么";
  ⑥ 需要"临时提交再回退"的验证,**换到隔离副本里做**(临时 worktree / 目录副本),
     **不要让验证动作动到主工作区的历史** —— 验证不该有破坏性预算。

### C1-R2 · 同一坑**第二次**出现 ⇒ 换工具,不是"再注意一次"

**规则**:同一个工具层的坑(引号/转义/shell 方言/编码/路径)在**同一段工作里出现第二次**时,
**停止依赖记性,改掉工具用法**。第二次是最好的信号:它证明"注意一下"对你无效。

- **反例(实例)**:把 Markdown 习惯(反引号 = 行内代码)带进 shell 字符串 ——
  反引号在 shell 里是**命令替换**。第一次(拼 `--body` 参数)靠"改用文件"绕过;
  第二次(拼提交信息)又踩,提交直接语法报错。**两次之间的"注意"没有生效。** *来源:见 §5。*
- **反例(实例 · 同一段工作里第三次发作,2026-09-13)**:**用脚本改文件**这件事**连栽三次** ——
  ① 改一张表格的某行 ⇒ **丢了一个单元格**;
  ② 改一份签核记录 ⇒ **把相邻条目的续行挪到了文件尾**;
  ③ 改一个演练脚本 ⇒ **整份改坏**(用来定位的切分**恰好切到了文件头** ⇒ 新内容替掉头部、旧内容残留),
  只能**整文件重写**。
  三次的**手段完全相同**:"**字符串切分定位待改段 + 只看命令退出码**"。
  前两次之后我已经对自己说过"下次注意" —— 第三次照样栽。**这正是本条说的:第二次就该换工具。**
  *来源:见 §5。*
- **正例(同一坑的换工具,对应上一条反例)**:**不再用切分定位** ——
  改用能**强制唯一匹配**的编辑手段(如按唯一子串替换的编辑器),或**整文件重写**;
  且**改完必须复核结构**:**语法检查**(`sh -n` 等)、**表格列数**、**关键串是否在位**。
  ⚠️ **退出码 0 不等于改对了** —— 它只说明"命令没报错"。

### `C1-R3` · 后台任务不要接管道

**规则**:把长任务放到后台跑时,**不要给它接 `| tail` 之类的管道** —— 管道会缓冲,输出不可见,
你只能靠猜它跑到哪了。要么**落文件**(`> log 2>&1`)再 `tail -f`,要么用无缓冲的前台分块运行。

- **反例(实例)**:后台命令接了 `| tail` ⇒ 进度不可见,只能反复猜"它到底在跑吗"。
- **正例**:输出重定向到文件;需要看进度时**另开一条** `tail -f`。

*来源:某评测门项目 · 2026-09-10 · 阶段3 收口。*

### `C1-R4 ⚠️` · CI 某步「0 秒失败」⇒ 先怀疑"命令根本没起来",不是"测试挂了"

**规则**:这是**最快的分诊判据** —— 测试失败要跑完整套(通常十几秒到几分钟),
**0 秒结束**说明命令在**解析/启动阶段**就退出了(参数被拼坏、命令不存在、语法错)。
⇒ 先看**这一步的 `run` 字符串最终是什么**,而不是去读测试输出。

**常见制造者:在 YAML 里手写 shell 续行符 `\`。**

- **反例(实例)**:某 CI 的 `run:` 写成多行、行尾带 `\`。YAML 的 **plain scalar 把换行折成空格,
  而反斜杠是字面量** ⇒ `\ ` 在 shell 里把空格转义 ⇒ `--a=1 --b=2` 被**拼成一个参数**
  ⇒ 命令立刻报用法错误。该步耗时 **0 秒**,而且**掩盖了同一 job 里另一个真失败**
  —— 两个红叠在一起,排查时只顾了一个。
- **正例**:① 多行命令用**块标量**(`run: |`),让换行被保留、`\` 才是真正的续行;
  ② 拿到"0 秒失败"先看**解析后的命令**,别先看日志尾巴;
  ③ 同一 job 里**可能同时存在多个失败**,修掉一个不代表全绿 —— **修完必须重跑看整条链路**。
- **可结构化的守卫(推荐)**:用脚本解析 workflow,断言每步的 `run` **不含 `\ `(反斜杠+空格)**
  —— 那正是"被折行拼坏"的签名。此类守卫要**突变验证**(把 bug 放回去,必须变红)。

*来源:某评测门项目 · 2026-09-12 · 定位"CI 自建立以来一直红"的过程(**两个真因叠加**)。*

### `C1-R5 ⚠️` · 清「已泄露的信息」前,先查**三条可达路径**

**规则**:要清掉已经推上去的敏感信息(邮箱 / 密钥 / 内部名),**先枚举它的可达路径**,再决定手段:

| 路径 | 强推能清掉吗 | 怎么查 |
|---|---|---|
| ① 分支历史(`main` 的 log) | ✅ 能 | `git log` / `git log -p` |
| ② **已合并的 PR 页面** | ❌ **不能** —— PR 会把旧提交保留在它自己的记录里 | 逐个 PR 查它的 commits(`gh api repos/<o>/<r>/pulls/<n>/commits`) |
| ③ **按 SHA 直查** | ❌ **不能** —— 对象仍在,可凭 SHA 取回 | 拿旧 SHA 直接查(`gh api repos/<o>/<r>/commits/<sha>`) |

⇒ **强推只清得掉 ①**;②③ 会一直留着,**而且没有任何东西提示你**。

**反例(实例)**:一次「清泄露」操作 —— 把 7 个提交压成 1 个干净提交并强推 ⇒ `main` 的历史**确实干净了**;
**但实测 ②③ 仍能读到旧邮箱**。若就此收工并宣布「已清干净」,交出去的就是一个**假结论**。

**正例**:① 先跑上面三条查询,拿到**真实**可达面;② 若 ②③ 也在(通常如此),**明确说"强推不能彻底清除"**,
并按影响面选:接受 / **删库重建**(自助、最彻底)/ 请平台支持清除;③ **优先堵源头** ——
把提交身份改成 `noreply`、账号层开「邮箱保密」⇒ 它**向前生效**,比清历史划算得多。

*来源:本库自身的公开仓运维 · 2026-09-12 · 一次「清泄露」操作(强推后,PR 页与旧 SHA 实测仍可达)。*

### `C1-R6 ⚠️` · 管道的退出状态是**复合**的 —— 它两个方向都会骗你

**规则**:`A | B` 的退出状态**既不是 A 的,也不是"整体成功/失败"**,而是由 `pipefail` 设置决定的**合成值**。
两个方向都会产出**假结论**:

| 方向 | 机制 | 你看到的 |
|---|---|---|
| **假失败** | `B` 命中即退出(`grep -q` / `head` 之类) ⇒ `A` 收到 **SIGPIPE** ⇒ 开了 `pipefail` 时整条管道判**失败** | "**没命中**" —— 而它**明明命中了** |
| **假成功** | `B` 正常读完(如 `tail`) ⇒ 管道状态 = **B 的** ⇒ `A` 的失败被**吞掉** | "**成功**" —— 而 `A` **失败了** |

⇒ 判据:**要判定 `A` 的结果,就不要把 `A` 放进管道**;
要用管道判"存在性",先确认**你拿到的退出码是谁的**。

- **反例(实例 · 假失败)**:一道**凭据扫描门**,三处判定都写成 `printf … | grep -q …`。
  `grep -q` **命中即退出** ⇒ 上游 `printf` 收到 SIGPIPE(141);而脚本开头有 `set -o pipefail`
  ⇒ **整条管道**状态变 141 ⇒ `if` 判成"**没命中**" ⇒ **真实命中被静默丢弃**。
  门**每次都打印"✅ 通过"**。实测同一份输入**连跑 20 次:拦住 11 次、漏报 9 次**;
  两个对照组(**分别只关 `pipefail` / 只去掉 `-q` 早退**)各自 **20/20**。
  ⚠️ 它**不是新引入的** —— 自该脚本第一版起就在。*来源:见 §5。*
- **反例(实例 · 假成功)**:同一段工作里另有一处写成 `命令 | tail -1` 取退出码 ——
  拿到的是 **`tail` 的 `0`**,于是"脚本失败"显示成"脚本通过"。**同一个人在同一天发作两次。**
  *来源:见 §5。*
- **正例**:① 判"**存在性**"用 `grep … > /dev/null`(**去掉 `-q`**,让它读完再判断)或 shell 内建的 `case` 匹配;
  ② 判"**某条命令的成败**"就把它**单独取出来**(`cmd; rc=$?`),**别接管道**;
  ③ 确需管道时,**显式声明你要谁的退出码**(如 bash 的 `PIPESTATUS`),或**明确关掉 `pipefail` 并写明理由**;
  ④ **概率性的门不能只跑一次** —— 见 `A5-R7`。

## 4. 适用场景与不适用场景

**适用**:
- 任何**收尾/确认**动作:合并了吗?清理干净了吗?推上去了吗?状态对了吗?
- 任何**批量操作**;
- 任何**破坏面不可见的命令**(批量删除 / `reset --hard` 之类的破坏性 git 命令);
- 任何**第二次**遇到同一个工具坑的时刻;
- **写 CI 的多行命令 / 排查 CI 失败** → `C1-R4`;**把长任务丢后台** → `C1-R3`;
- **清理已泄露的信息** → `C1-R5`(先查三条可达路径,别只强推了事);
- **用管道下判断** → `C1-R6`(`grep -q` 会假失败、`| tail` 会假成功)。

**不适用 / 注意**:
- **确定性、可复现的失败**不用本文 —— 直接修即可,不必上升到规则;
- **一次性、无后果的操作**(比如看一眼状态),不必强求双判据;
- 本文**不是**"所有事都要验证两遍"—— 它只要求:**当你声称"已完成"时,你的判据要能反映那件事**。

- 实例(`C1-R6` · 假失败):`某 RAG 服务项目` · 2026-09-17 · 单模块测试闭环轮。
  一道**凭据扫描门**用 `printf … | grep -q …` 判定命中,而脚本开头有 `set -o pipefail`。
  该门**自建立之日起**就有 ~一半概率漏报。发现方式**不是设计审查,是"不信一次结果"** ——
  修复另一处缺陷后按纪律重跑验证,发现探针**时灵时不灵**,坚持跑 20 次才看见 11/9。
- 实例(`C1-R6` · 假成功 / `C1-R1` · 破坏性命令):**同一人、同一天**、同一次工作里另两处 ——
  用 `cmd | tail` 取退出码(拿到 `tail` 的 0),以及用 `git reset --hard HEAD~1`
  撤销一个临时提交(抹掉当天全部未提交产出)。

## 6. 怎么验证它被落地

1. **可证伪的自查句**:说"我确认已完成"之前,问 —— **"这个判据,在那件事没成的时候会变红吗?"**
   答不出(例如"只能看到它说未合并,但它一直这么说")⇒ 换判据。
2. **可识别的坏味道**(出现即停手):
   - 判据输出**全都一样**(全绿 / 全失败 / 全"未合并") —— 先怀疑判据失效,再怀疑对象;
   - 批量操作里**同一行错误重复 N 次**;
   - 你在心里说"注意一下引号/转义"——那是 `C1-R2` 的触发点,不是解决方案。
3. **工具层的最小固化**:把"含特殊字符的内容一律走 heredoc/文件"写成模板或段落,
   让下一次**不需要记得**。
4. **CI 分诊可用**:CI 日志里"某步 0 秒失败"时,能否**立刻**拿到该步解析后的命令?
   (能 ⇒ `C1-R4` 落地;要先翻 YAML 才知道 ⇒ 还没落地)
5. **后台任务可观察**:长任务输出**落文件**、进度可 `tail -f`(而不是接了管道看不见)。
6. **清泄露的结论可证伪**:宣布「已清干净」前,能否指出**三条可达路径各自的实测结果**?
   只查了①就宣布 ⇒ 按 `C1-R5`,那是假结论。
7. **管道判断可证伪**(`C1-R6`):脚本里凡 `if A | B` 式判定,能否指出**它拿到的是谁的退出码**?
   判"存在性"的 `grep` 是否**去掉了 `-q`**(或改用了 shell 内建匹配)?
   ⚠️ 更硬的一问:**这个判定是概率性的吗?** 是 ⇒ 必须有**重复 N 次、报告拦/漏计数**的记录
   (一次运行证明不了任何事;见 `A5-R7`)。
8. **破坏性命令可证伪**(`C1-R1` 第 2 类):跑 `reset --hard` / `checkout -- .` / `clean -fd` 之前,
   有没有**先把 `git status` 的结果看一眼**?事后能指出"我当时要损失的是什么"吗?
