# Agent 避坑库 · 收录标准与写法约束(唯一权威)

> 本文件是**本库的约束来源**。任何一篇的内容与命名,若与本文件冲突,**以本文件为准**。
> 本库**会被整体移动/改名**(可能换目录、换上级路径)⇒ 库内一切内容**不得依赖库外文件才能读通**。

---

## 1. 读者是谁(这条决定一切)

**唯一读者 = AI Agent。** 人是维护者、不是读者。

⇒ 由此推出三条硬要求:

1. **写规则,不写感想。** 每条必须是"Agent 读了能照做"的动作;不写情绪、不写"我们要重视"。
2. **不许要求读者去库外翻东西。** 库外的东西对读者**不存在**(他拿不到、也不该去拿)。
3. **能被扫读。** Agent 是按需检索 + 读局部,不是从头读到尾 ⇒ 标题要能直接命中主题,规则要能独立成立。

---

## 2. 收什么(两条尺子,必须同时满足)

### 尺子一 · 严重性

**不报错、不变红,却能让"错的结论被当成正确的结论交付"**,或**系统性地把 Agent 的行为带偏**。

- 典型形状:静默降级 / 验证动作永远不失败 / 判据结构性失效 / 结构本身腐烂;
- 反例(不收):"这次命令写错了"这种**报错即止**的错 —— 它自己会喊,不需要进库。

### 尺子二 · 领域

**必须是 Agent 系统 / harness 系统 / AI 系统本身的问题。**

判定问法:**"把 Agent 换成一个普通工程师,这个坑还成立吗?"**

- 成立 ⇒ 按尺子一判,**够严重**才收(进 B/C/D 区,见 §4);
- 不成立(只对 Agent/harness/AI 成立)⇒ 优先收进 **A 区**。

---

## 3. 不收什么(明确列出,防"越写越宽")

| 不收 | 去哪 |
|---|---|
| 通用 shell / git / CI / 环境 / 依赖 的操作坑 | **B / C / D 区**(仍收,但**不进 A 区**) |
| 单个项目的流程规约、目录约定、团队分工 | **不收** —— 那是项目文档,不是避坑规则 |
| 一次性环境故障(某机器的网络、某天的额度) | **不收** —— 它不可复用 |
| 纯管理/协作话题(排期、评审文化、汇报) | **不收** |
| 只对**人**成立的判断技巧 | **不收**(读者是 Agent;若同时对人有用,按"对 Agent 有用"写) |

> ⚠️ **一个具体的判例**:「规则要写到反直觉的边界情形上」这类**写判据的方法论**,
> 只有当它落在 **AI 判分器/人工参照校准**这个场景里才收(→ A 区);
> 若只是泛泛谈"怎么给人写说明",**不收**。

## 4. 目录与分区

```
18.Agent避坑库-问题解决策略/
├── README.md                      ← 本文件(约束;不参与编号)
├── A-AgentSystem系统/             ← 严重的 Agent/harness/AI 系统问题
├── B-Flake偶发失败与归因/          ← 偶发故障、归因方法
├── C-ShellGit命令与批量操作/       ← shell / git / 批量 / 引号转义 / CI 配置
└── D-EnvBuild环境依赖与构建/       ← 环境、依赖、镜像、构建产物
```

**分区规则**:

- **区 = 题材域**,不是重要性分级。A 区是"Agent 系统本身";B/C/D 是"通用工程,但按题材细分"。
- **不收的域不建区**。某区**只有一篇**时仍可独立成区(便于日后生长);
  若某区长期为空 ⇒ **删掉该区**(不保留空壳)。
- 新增区的条件:出现**≥1 条**规则,且**现有区都不合适**。
  ⇒ 先问"能不能放进现有区";放不进,才建新区,并在本文件 §4 登记。

## 5. 命名规则(文件夹与文档)

**中英并列**:英文标识在前(为了**英文检索命中**)、中文标题在后(为了**语义可读**)。

| 对象 | 格式 | 例 |
|---|---|---|
| 区目录 | `<字母>-<EnglishSlug><中文域>` | `A-AgentSystem系统` · `B-Flake偶发失败与归因` |
| 文档 | `<区字母><序号>-<english-slug><中文标题>.md` | `A2-skills技能触发失效.md` |

**EnglishSlug 的取法**:用**行业通用写法**,便于检索 ——

- **能小写就小写**(与行业一致):`skills` · `hooks` · `git` · `shell` · `env` · `build` · `flake` · `judge`;
- **复合词用大驼峰**:`AgentSystem` · `SubAgent` · `EnvBuild` · `ShellGit`;
- ❌ 不要自造词(如 `SkillIssue`)、不要拼音。

**序号**:区内两位递增(`A1…A9`);**新篇追加在末尾,不重排既有序号**(序号稳定 > 序号好看)。

---

## 6. 规则编号

**格式:`<篇ID>-R<篇内序号>`**,如 `A2-R3`、`C1-R2`。

- ✅ **全局唯一**(彻底避免"同一编号指两条规则"的历史问题);
- ✅ 篇内连续 ⇒ 增删条目不牵动别篇;
- ✅ **库被移动/改名不影响规则 ID**(只影响文件名);
- ⚠️ **规则搬家 ⇒ ID 会变**:搬家时**必须**在该篇「变更记录」里写 **`旧 ID → 新 ID`**;
- ❌ 全库连续编号(如 R1–R99)**禁止** —— 它必然产生跨篇冲突。

**跨篇引用**:**只写篇 ID 或规则 ID**(如"见 `A4-R2`"、"见 A3 篇"),
**不写文件名、不写"第 N 篇"**(文件会改名、会被移动)。

---

## 7. 每篇体例(必备五节,缺一节即不合规)

1. **一句话结论**(最值得留下的那句,放最前)
2. **规则**(每条:`规则(通用)` → `反例(实例)` → `正例(怎么做到)`)
3. **适用场景与不适用场景**(读者要能判断"这条对当前任务适不适用")
4. **来源**(事件描述,见 §8)
5. **怎么验证它被落地**(可证伪:违反它时,**有没有东西会变红/出声?**)

> 没有第 5 节的策略 = "只有文字",**等于没落地** —— 这是本库的立库之基。

## 8. 路径约束(硬性)

> **背景**:本库会被移动;单个项目做完/改名/重构后,写进库的路径**必然失效**。
> 已发生过:某篇断言"某目录下不存在 X",而该目录后来被补上了 ⇒ 声明**变成失真**。

| 允许 | 规则 |
|---|---|
| ❌ **项目产物路径**(`docs/复盘/xxx.md`、`<某项目>/tools/yyy.py`) | **禁止**。来源只写**事件描述**:`<项目代号>` + 日期 + **哪一次实战**(如"2026-09-12 · 某评测门项目 · M1 人工标注轮") |
| 🟡 **约定位置**(`.claude/hooks/`、`.githooks/commit-msg`、`CLAUDE.md`、`tests/`、`tools/`) | 可写,但**必须声明这是跨项目的约定位置**,不是某个项目的产物 |
| 🟡 **具体脚本/文件名**(如 `check-skill-coverage.sh`) | 可写,但**必须加前缀**「**示例(本仓实现)**」—— 否则会被读成"标准要求" |
| 🟢 **叙事里的示意文件名**(如「给 `rules.py` 加个函数」中的 `rules.py`) | 可写,**无需逐个标注** —— 它是**举例**,不是路径、也不要求读者去找它 |
| 🟡 **harness 运行时目录**(session / transcript 等) | **必须用占位符** `<…>`,如 `<session_dir>/tasks/*.output` |
| ❌ **`第 N 篇`式引用** | 禁止(见 §6):改用篇 ID |

**检查范围**:校验脚本扫**所有入库文件**(不只 `.md`)—— `tools/`、`.github/`、`.githooks/` 同样在列。
**唯一豁免**:`tools/check_kb.py` 自身 —— 它按定义就写着那些模式串与自测样本,否则会自己抓自己。
⚠️ 代价:该文件里的**真**泄漏不会被它自己发现 ⇒ **改它时要人工过一眼**。

**自检句(可证伪)**:把本库**整体挪到一个全新位置**,删掉一切库外文件 ——
**这篇还读得懂、还照做得了吗?** 读不懂 ⇒ 不合规,回去改。

## 9. 维护流程

| 动作 | 规则 |
|---|---|
| **新增一篇** | 先判 §2 两条尺子;不满足 ⇒ 不收(或收进 B/C/D);新篇追加区内最大序号 |
| **新增一条规则** | 追加到**已有篇**的末尾(不新建篇),编号取该篇下一个序号 |
| **规则搬家** | 允许(内容按规则拆,不必整篇移动);**必须**在迁出/迁入两篇的变更记录里写 `旧 ID → 新 ID` |
| **合并两篇** | 允许;旧篇删除,其规则 ID 在新篇里**重编并留映射** |
| **删除** | 仅当**规则被证伪**(实证不成立)或**并入他篇**;删除**必须**写理由 —— **"删一条教训 = 丢掉一条教训"** |
| **整库移动/改名** | 允许且预期;**移动后必须做的自检** = §8 的自检句 |
| **改库前先跑校验** | `python3 tools/check_kb.py`;带 `--self-test` 可做**突变验证**(检查器自身有没有防腐)。CI 与本地 pre-commit **跑的是同一份** |
| **用户级提醒门(可选)** | `tools/kb-write-guard.sh` —— 装到 `~/.claude/hooks/` 并在 **`~/.claude/settings.json`**注册 `PreToolUse`(matcher `Edit|Write|NotebookEdit`)。它**故意不对称**:主会话 ⇒ `ask`;**子 Agent ⇒ 只注入提示、不 ask**(子 Agent 无人批准,ask 会把它挂死)。⚠️ 为什么必须放**用户级**:settings **只从 cwd 的 `.claude/` 加载,无父目录回退** ⇒ 本库自带的 `.claude/` 在别的项目里不被读。<br>**判据锚点(按序,不是并列)**:① 读 `~/.claude/kb-avoid-pitfalls.dir` 指向的目录,**该目录真的存在** ⇒ **只认它**(被写路径落在它里面才算命中);② 没配 / 配的目录**已不在** ⇒ 降级到**路径分量整段等于库名**(**不做子串匹配**)。<br>⚠️ **库改名 / 搬走 ⇒ 改那个 `.dir` 文件** —— ② 只认整段相等,认不出新名字。跑 `--self-test` 会打印**本机当前走的是 ① 还是 ②**;判据为什么长成这样,见 `C1-R7` |
| **本地左移门** | `git config core.hooksPath .githooks` —— ⚠️ **每台机器装一次**,**不随克隆/移动携带**(本库 A1 篇对此有专门教训) |
| **终门(CI)** | GitHub Actions `kb-check`(push / PR 必跑);`main` 已开**分支保护** ⇒ 改动**须走 PR + 必需检查** |
| **合并方式** | **先有「可以合」那一句,再走 auto-merge。** 取得该句后 `gh pr merge --auto --squash`,CI 绿即自动合,**不再问第二遍"现在合吗"**。<br>⚠️ **`gh pr merge` 本身就是对外动作** —— 它把内容落地到主干、成为既成事实,受 `A7-R1` 管:**必须能指出一条显式指令**。**CI 绿是质量判断,不是授权。**<br>⚠️ **Agent 自己开的 PR 尤其不许自合** —— 那等于**自产自合,整条链上零次人工确认**。单人仓里「点合并」就是唯一的人工审核位。<br>⚠️ **本行原版写「默认开,无需人工点」,与 `A7` 直接冲突** —— `A7` §6 的对外动作清单里**就列着 `gh pr merge`**。两者不可同时成立(装了那道门,auto-merge 会被 `ask` 拦)。⇒ **已按 `A7` 更正**(2026-09-15)。 |
| **仓库安全设置(公开仓)** | 已开 **Secret scanning + Push protection** ⇒ 误提交密钥会在**推送时被拦**(这是"结构 > 提醒"在仓库层的体现)。⚠️ 若你被 push protection 拦下,**那不是故障** —— 是它按设计工作;确认内容无密钥后按提示放行或改写历史。|
| **库被移动/改名之后** | 跑一次 `python3 tools/check_kb.py`:它**不依赖任何绝对路径**;校验通过即说明库**仍自洽**(§8 自检句的可执行版) |
| **提交身份** | 本仓提交**必须用 GitHub `noreply` 身份**(真实邮箱会公开在 commit 元数据里,且**强推清不干净** —— 见 `C1-R5`)。**两层都已上结构**:① 本机 `git config --global user.email` = noreply;② 账号层 GitHub → Settings → Emails 已开「Keep my email addresses private」+「Block command line pushes that expose my email」⇒ 网页/API 侧创建的提交(含**合并 PR**)也会被改成 noreply,且带真实邮箱的 push 会被**拒绝**。勿改回 |
| **本库已纳入 git** | 每次改动 = **一个 commit**(新增/搬规则/改编号,都写进 commit message);**规则搬家必须**在提交信息里带上 `旧 ID → 新 ID` —— 库被移动时 git 历史是唯一可回溯的锚 |
