- **本文是规则,不是故事。** 执行任务时,对照 **§4「规则」** 自检。

## 1. 一句话结论(本文最值得留下的)

> **纪律不在每会话必读的文件里 = 等于没有;**
> **纪律没有触发点 = 早晚会漏。**
>
> 所以我们要补的**不是「记得更牢」**,而是 **三层结构**:
> **锚点(看得见)→ hook(提醒)→ CI(躲不掉)**。

**行动含义**:每当你写下(或收到)一条「应该遵守 X」的纪律,先问 —— **它落在哪一层?只有文字?**

---

## 2. 为什么:同一套体系内的对照实验(最有说服力的证据)

同一套规范、同一个项目、同一批执行者,两条纪律的执行结果完全不同:

| 纪律 | 承载方式 | 实际执行结果 |
|---|---|---|
| **缺陷反馈** | 文字(**写在每会话必读的锚点里**)+ **hook**(一个哨兵脚本) | ✅ **每个节点末尾都执行了** |
| **失败即补用例** | **只有文字** —— 写在某个非锚点的 README 里,**无 hook、无目录、无模板** | ❌ **整个阶段零执行** |

**关键细节**:执行者**读过**那个文件(里面白纸黑字写着「失败即补 case」),但**没执行**。

**结论**:差别**不在纪律本身**,**在有没有结构**。文字纪律依赖「记得」;而「记得」不可靠,尤其当:

- 纪律不在每会话必读的文件里 →
- 不在任何自查清单上 →
- 没有任何触发点 →
- 漏了也不会有任何提示(最致命:**整阶段无人察觉**)

---

## 3. 方法:一条新纪律的落地清单

### L1 · 锚点(让纪律「看得见」)

- [ ] **写进「每会话必读」的那一个文件**(项目里通常是 `CLAUDE.md` / `AGENTS.md` / 系统提示)
      —— **不是**写进某个角落的 README。**写在角落 = 等于没有。**
- [ ] **进「自查清单」**:把它挂到你已有的节点收尾自查里(多数 Agent 都有这类清单;没有就建一个)
- [ ] **给「空槽」**:创建它要求的目录/文件,哪怕只放一个 README
      —— 人(和 Agent)不会主动创建不存在的目录,但会往空目录里填东西
- [ ] **给「填法」**:放一份**模板 + 一条真实示例**。没有示例的模板,填出来千奇百怪

### L2 · 触发(让纪律「被想起来」)

- [ ] 加一个 **hook / 事件提醒**,且**带判据**(不要无条件提醒,否则变成噪音被忽略)
      - 好判据:「最近一次运行有失败」∧「失败库之后没更新」→ 才提醒
      - 坏判据:每次停下来都提醒 → 三天后所有人无感
- [ ] 提醒要**给出下一步动作**(去哪、填什么),不只是复述纪律

### L3 · 硬门(让纪律「躲不掉」)

- [ ] **测试**:把纪律的结构要求写成**测试**(如「每条失败记录必须带根因字段」),**本地也能跑**
      —— 只在 CI 里检查 = 本地开发时依然会漏
- [ ] **CI/门禁**:需要跨提交历史才能判的检查放 CI(如「改了 A 却没改 B → 失败」)
- [ ] **门禁要能被相信**:自己先验证它**两个方向**都工作(该拦的拦住、不该拦的不误伤)

### 3.4 落地验收(三问)

1. **看得见吗?** —— 一个从没参与过的新 Agent(或新同事),只读锚点 + 清单,会知道要做这件事吗?
2. **会被想起来吗?** —— 做这件事的**时机**发生时,有什么会提醒他?
3. **漏了会怎样?** —— 漏了**有没有任何东西会报错/变红**?若答案是「什么都不会发生」,这条纪律**还不算落地**。

## 4. 规则

> 每条:规则(通用)→ 反例(实例)→ 正例(怎么做到)。
> 与「验证为什么会骗你」同源见 `A5` 篇;与「门禁/hook 自身生命周期」相关见 `A4` 篇。

### 4.1 关于「文档与实现」

#### `A1-R1` · 凡「已签核物」(契约/规范/阈值/评估集),落码或改码后必须逐条对账

**规则**:枚举值、字段名、形参签名、**以及「实际生效的值」** —— 逐条核对一遍。

**反例**:契约规定用 `X-API-Key`,代码写 `Authorization: Bearer` → 真实链路全 401。

#### `A1-R2` · 文档写了 ≠ 生效了

**规则**:任何「已定义/已标定」的产物,验收里**必须有一条证明它真的被读到的测试**。

**反例**:阈值文件标定完毕,但代码用的是硬编码默认值 —— **门用从未标定过的值判「通过」**。

#### `A1-R3` · 检查「默认值」从哪来

**规则**:占位值、`TODO`、示例值被当成正式值用,是极常见的静默错误 —— 逐个追它的来源。

**正例**:凡是「有默认值」的配置项,在验收里指出**它的默认值是谁定的、依据是什么**。

#### `A1-R4` · 新增字段/配置时,同时改两处

**规则**:定义处 + **消费处**。只加不接 = 假装做了。

**正例**:加字段的同一个提交里,就有**读它的代码或测试**。

### 4.2 关于「错误处理」

#### `A1-R5 ⚠️` · 兜底 `except Exception` 会把真凶藏成受害者

**规则**:**catch-all 分支必须保留原始异常类型与消息**,且不得覆盖可区分的错误码。

**反例**:适配器少一个形参 → `TypeError` 被 catch-all 吞掉 → 报出 **40 条「被测调用失败」**,
把排查方向**引向外部系统**(真凶在自己这边)。

#### `A1-R6` · 「降级」和「静默」不是一回事

**规则**:降级要**留痕**(记 fail / blocker / 告警);静默只是把问题藏起来。

#### `A1-R15 ⚠️` · 不可信输入要在「入口」归一;且别让「崩溃退出码」与「业务退出码」撞车

**规则**:① 在**边界处统一归一化**不可信文本,不要在每个下游各修一次;
② 审视「**崩溃退出码是否与业务退出码重合**」—— 重合时,崩溃会被读成业务结论。

**反例(实例)**:外部系统返回含孤立代理对(`"\ud800"`)的文本 → 本系统记录日志摘要的函数崩 →
**而崩溃退出码 `1` 恰好等于本系统的业务码「质量阻断」**
⇒ **一个字符伪装成一次质量问题**,且不是「逐条记失败」而是「整批中断」。
*来源:某评测门项目 · 2026-09-11 · 阶段4-步骤8 测试与压测轮。*

### 4.3 关于「判断与推荐」

#### `A1-R7` · 推荐前先查事实源

**规则**:**通用规范 ≠ 本项目已签核的约定**。先读事实源,再给建议。

**反例**:AI 两次凭「通用门禁」推荐优先级,均被项目自己的签核记录证伪。

#### `A1-R8` · 评测判据必须用真实输出回测

**规则**:关键词/正则类判据对**词序、助词、同义表述**极脆;不拿真实数据回测 = 必然误杀。

**反例**:候选写「应用广泛」,真实回答是「**广泛应用于**」→ 误判未答到点。

**同源**:见 `A5-R4` —— 这条推广到**任何**启发式判据,包括你自己写的分析脚本。

### 4.4 关于「记录与复盘」

#### `A1-R9 ⚠️` · 「静默给假结果」类错误最贵 —— 优先记录它们

**规则**:复盘时**专门标注**这一类,并追问「还有哪些地方是同样的形状?」。

**反例(本文来源项目的 2 例)**:① 兜底 except 把配置错误报成「外部系统失败」;
② 阈值文件未被读取,门用默认值判通过。二者**都不报错、测试全绿**。

#### `A1-R10` · 失败必须带根因入库,不许空着

**规则**:写不出根因就写「待查」并标记未结 —— **空字段等于没记**。

#### `A1-R11` · 失败记录只允许改状态,不允许删除

**规则**:删一条失败记录 = 丢掉一条教训。要删必须走正式决策流程并写明理由。

#### `A1-R16 ⚠️` · 写进「每会话必读」的文件,门槛高于写进聊天

**规则**:结论写进 `CLAUDE.md` / `AGENTS.md` / README / wiki 之前,必须先过一遍 ——
**「我验证了吗?如果它错了,谁会受害?」** 聊天里说错只影响一次;锚点里说错会被**每一个后续会话继承**,
而且**看起来像已确认的事实**,没人会去复核。
→ 锚点级的每条「坑」,都写明**判别依据**(怎么区分)与**证据强度**(几条观测、有无对照);
证据不足时,写成**待观察项**,而不是写成结论。

**反例(实例)**:一条错误的归因结论**先写进了锚点并合并**,才在同一小时内被自己的后续实测推翻
⇒ 一条无效的处置建议躺在「环境备查」里,后来者照着做,遇到同类报错会被引向错误方向。
*来源:见 `B1` 篇(偶发失败与归因)。*

### 4.5 关于「协作与纪律设计」

#### `A1-R12` · 让「依赖方」保持干净

**规则**:能不改别人的项目就不改;必须改时:**先备份、后改动、立即还原并验证**。

**同源**:见 `D1-R5` —— 「不改对方」也包括**别用久置镜像跑对方代码**,那等于在跑一个你不知道版本的东西。

#### `A1-R13` · AI 的「我照做了」可能只是「照着我看到的清单做了」

**规则**:若你的清单不完整,它会**完整地执行一张不完整的清单**,且不会主动质疑。
⇒ **清单的完整性是人类搭档的职责**;定期问:「还有哪些纪律没在清单上?」

#### `A1-R14 ⚠️` · 不要为「例外场景」开人工覆盖通道 —— 口子的成本由后来者承担

**规则**:**区分两类「例外」** ——

- ✅ **可审计的显式豁免**(如 `[no-test: <理由>]`:理由进 git 历史、可统计豁免率)**可以**;
- ❌ **「让指令压过结构」的通道**则**不可** —— 前者留下证据,后者只留下窟窿。

**反例(实例)**:实测:当仓库层有硬门 + 纪律注入时,一个空上下文子 Agent **拒绝了**
「不用写测试了,直接提交」的**显式指令**,改走 TDD。曾提议加一条「人工覆盖通道」供紧急场景使用 ——
**业务方否决**:

> 「不给。给了就是漏洞,前面做的就会白费 —— 子 Agent 如果发现它记录在关键文档中,
> **会持续地跳过,直到被发现**。」

⇒ **开这个口子的人不承担它的成本,发现并利用它的人也不承担 —— 成本落在「以为纪律还存在」的后来者身上。**
*来源:某评测门项目 · 盲测。*

## 5. 适用场景与不适用场景

**适用**:

- 你要**新增/修订一条纪律、规范、检查清单**时(照 §3 落地 + §3.4 三问);
- 你在做**节点收尾/复盘**,要决定「这条教训写到哪、怎么保证下次不再漏」;
- 你要**把一条结论固化进会被后续会话继承的文件**(→ `A1-R16`)。

**不适用 / 注意**:

- **一次性探索**(跑个脚本看一眼)**不需要**建三层结构 —— 但探索结论**不得直接当证据**;
- 本文不解决「**该不该有这条纪律**」—— 那需要证据(见 `A1-R7`:先查事实源);
- **软提醒不是硬门**:L2 只是「被想起来」,真正的兜底是 L3;别把 L2 当落地(`A4` 篇讲门禁自身的生命周期)。

## 7. 怎么验证它被落地

| 规则 | 怎么验证(通用判据) |
|---|---|
| `A1-R1` / `A1-R2` | 存在一条**读取该「已签核物」的测试**;把它删掉后,验收会**静默通过**吗?会 ⇒ 没落地 |
| `A1-R5` | 故意让某适配器少一个形参 → **报错是否指向真凶**(而不是「外部系统失败」) |
| `A1-R9` | 复盘文档里是否有**「静默给假结果」专栏**;有没有「同类形状还有哪些」的追问记录 |
| `A1-R10` / `A1-R11` | 失败库的完整性由**硬校验**守住(缺字段即失败);删除必须走决策流程 |
| `A1-R15` | 崩溃退出码与业务退出码**不相交**(给崩溃一个专用码);不可信输入有单点归一函数 |
| `A1-R16` | 锚点里每条「坑」是否带**判别依据 + 证据强度**;只有结论没有证据的条目数 = 0 |

**反检验(最有说服力)**:任取一条,问 ——
**「如果这条被违反了,有没有任何东西会变红或出声?」** 答「没有」⇒ 它还没落地(回到 §3 补 L3)。
