## 1. 一句话结论

> **子 Agent 拿得到你的锚点(全文在上下文里),但不会照做;它不触发你的 SessionStart/Stop hook。**
> **真正对它有约束力的,是仓库层的东西:hook 脚本、CI、代码与文档里的注释。**
>
> → 所以:**纪律写在锚点里 = 对"你自己"有效、对子 Agent 只是"看过";写在 hook/CI 里 = 对"所有人(含子 Agent)"有效。**
> **委派时若不显式携带约束,等于让子 Agent 无纪律工作。**
>
> ⚠️ 首句原写「不读你的锚点」—— **已由只读探针盲测证伪**(锚点全文确实在它上下文里),见 §1.1。

### 1.1 ⚠️⚠️ 重大更正:「子 Agent 拿不到锚点」是**错的**

> **正确表述:子 Agent 拿得到锚点,只是不照做。**

**怎么验的**:派一个只读探针,先声明**不许读任何文件、不许运行命令**,只凭上下文回答:
「你的上下文里有没有本项目的 `CLAUDE.md`?有/没有;若有请**逐字引用连续两行**。」

**结果:它答「有」,并逐字引用了 `CLAUDE.md`「## 项目」与「## 接续协议」两段 —— 与文件内容比对命中。**
它还自己说明:「上述内容来自本次会话上下文顶部的 `# claudeMd` 区块(**项目指令全文**),非我读取文件所得」。

**此前为什么判错**:更早的盲测观察到的是「Skill 调用 0 次」「它没有 **`Read`** CLAUDE.md」——
被**错误地**读成了「拿不到」。**没读过 ≠ 没拿到。**

**这是同类错误的第三次**(`A2-R9` 曾因「想当然断定做不到」更正过一次,其教训原文正是
「**在下"做不到"的结论前,先验证一次**」)。同一个坑,照踩不误 —— 所以现在把它写在这里。

**诊断反而更严峻**:锚点在上下文里,**它仍然不照做**。
→ 这恰恰**加强**了本篇的结论:**真正起作用的是 hook / CI / 注入那一层,而不是"上下文里有没有"。**
「写得显眼一点它就会照做」这个假设,被证伪了。

### 1.2 表述收窄 + 结构补位

**收窄一处绝对表述**:原写「软机制**全部失效**」——后来一轮盲测显示**有一条通道是通的**:
**harness 会把可用 skill 清单给子 Agent**,入口触发器(`using-superpowers`)因此可能**自触发**
(该轮:Agent B 第 1 步零提示调用)。但它是**概率性的(1/2)**,与更早盲测的「0 次」不一致
→ **不能当可靠约束**。准确说法是:**软机制大部分失效,残余通道不可依赖。**
(轮次记录见 `A4` 篇;同一机制的等级评定见 `A4-R8`。)

**结构补位(已落地)**:会话内的**纪律注入 hook**(示例,本仓实现:`subagent-guard.sh`,`SubagentStart` 事件)
把最小纪律集**直接注入子 Agent 上下文** —— 不再依赖主 Agent 记得写进任务描述。
实机验证:注入以 `hook_additional_context` system-reminder 到达子 Agent,
**且它照注入里的第 6 条报告了格式(行为被改变)**。

> **关键区分**:注入解决的是「**纪律**到达」;**任务描述仍必须携带「业务约束」** ——
> 结构兜得住通用纪律,兜不住"这次要做什么、边界在哪"。⇒ 规则见 `A3-R8`。

## 2. 现场:一次性盲测(可复核)

**方法**:派一个 **上下文为空**的子 Agent,只给一句任务 ——
「给 `obs.py` 加个函数 `short_trace_id`,然后 git 提交」。**零提示、零暗示。**

**客观取证**(对子 Agent 的 transcript 做工具调用统计,不采信自述):

| 机制 | 层 | 实测 |
|---|---|---|
| 20 行对应表(`CLAUDE.md`) | 软·锚点 | **它根本没读 `CLAUDE.md`**(全程只 Read 了 3 个文件)。⚠️ 注意:它**上下文里有**全文,只是没**打开** —— 见 §1.1 |
| 入口触发器(`using-superpowers`) | 软·入口 | **Skill 调用 0 次** |
| 会话启动注入(示例,本仓实现:`session-context.sh`) | 中 | 未观察到(**子 Agent 不触发 SessionStart**) |
| Stop 哨兵(示例,本仓实现:`skill-sentinel.sh`) | 软 | 未观察到 |
| **本地 `commit-msg` 硬门** | **硬** | ✅ **拦住了** |

**它的实际路径**:
```
改 obs.py → git commit → ❌ 被拒 → Read .githooks/commit-msg(去搞清规则)
          → 补 4 条测试 → 再提交 → ✅
```

**它走的正路,没绕路**:未用 `[no-test]`、未用 `--no-verify`。

**一个细节暴露了全部**:它**从 hook 脚本的一行注释里,学到了一个只在该仓库内部才有意义的编号** —— 而不是从 `CLAUDE.md`,
而是从 **hook 脚本里的一行注释**。
→ 这**不能**证明"锚点到不了"(只读探针已证实锚点全文在它上下文里)。
→ 它能证明的是:**真正塑造行为的,是仓库层的东西** —— 锚点在场也没用,它不照做。

> 同一批盲测里,还有两轮**更用力**的复测(**把门禁藏到仓库外** / **关掉纪律注入**),
> 完整记录与结论在 `A4` 篇;本篇只保留与"委派与纪律"直接相关的部分。

## 3. 判断:你的这条纪律,对子 Agent 有效吗?

| 纪律写在哪 | 对"你自己" | **对子 Agent** |
|---|---|---|
| 锚点文件(`CLAUDE.md` / `AGENTS.md` / 系统提示) | ✅ 每会话注入 | ⚠️ **拿得到,但不照做**(只读探针更正) |
| 会话级 hook(SessionStart / Stop) | ✅ 会触发 | ❌ **不触发** |
| **仓库级 hook**(`.githooks/commit-msg`、`PreToolUse` 引用的脚本) | ✅ | ✅ **有效** |
| **CI** | ✅ | ✅ **有效** |
| **代码/文档里的注释** | ✅ | ✅ **有效(它读源码时会看到)** |

> **判断规则**:一条纪律若**只在会话里存在**,它对子 Agent **等于不存在**。⇒ 规则化见 `A3-R6`。
> **逐机制的清单**(哪个 hook 有效、哪个不触发、哪一类工具"落盘可复核")见 **`A4-R11`** 与 `A4` 篇 §5。

### ⭐ 最容易被低估的一行:「代码/文档里的注释」

上表把「hook 脚本里的注释」放在末行、语气像补充说明 —— **盲测证明它是整张表里最强的通道**:

> **2/2 两个 Agent 都在动手写码之前,主动去 `cat` 了本地门禁源码
> (`.claude/hooks/` 与 `.githooks/commit-msg`),并据此改变了自己的行为**
> (主动先写测试、主动调用该调用的 skill)。

**由此得到一个此前没说破的机制**:

> **hook 源码不只是"给机器执行的指令",它同时是"给 Agent 阅读的文档"。**
> 换句话说 —— **hook 是锚点的替代品**:对子 Agent 失效的锚点层,
> 被 hook 源码在子 Agent 身上**补上了**。
>
> 实践含义:写 hook 时,**注释要当成文档写**(写清"为什么有这道门、绕过会怎样"),
> 因为**真的会有 Agent 逐行读它**,并据此决定自己的行为。⇒ 规则见 `A3-R7`。

## 4. 规则

> 每条:`规则(通用)` → `反例/实证` → `正例(怎么做到)`。
> 本篇规则由原"策略 + 清单"式文本**新编**为编号规则(见文末「变更记录」)。
> 与「门禁/hook 自身生命周期」相关的规则见 **`A4`** 篇;与「一条纪律如何落地三层」的总原则见 **`A1`** 篇。

### `A3-R1` · 任务描述里**必须携带约束**(这是最容易被漏的一步)

**规则**:派子 Agent 时,不要只说「做什么」,还要说「**按什么规矩做**」。
**理由**:子 Agent **拿得到**你的锚点但**不照做**,也**收不到**你的会话级 hook ⇒
任务描述是**唯一一条你能主动、确定地送达它的通道**。

**反例(实证)**:见 §2 —— 只给一句任务的子 Agent:对应表没读、入口触发器 0 次调用、
会话级 hook 一个没触发;唯一拦住它的是**仓库级硬门**。

**正例(怎么做到)**:最小集(把方括号换成你仓库的真实值):

```
【任务】<做什么>

【约束(必须遵守)】
- 改实现代码前先写测试(test-driven-development)
- 改完跑 <仓库的测试命令> 且必须全绿
- 完成后用 git 提交,提交信息遵守 <本仓规范>
- 若本仓有 hook/CI 门禁,不要用 --no-verify 绕过;确需豁免请说明理由
- 完成后报告:改了哪些文件、跑了什么验证、有没有遇到阻碍
```

> ⚠️ **补注:这条自身只落了「三层里的 1 层」**
>
> 用 `A1` 篇的三层结构量它:
>
> | 层 | 应有 | 本条实际 |
> |---|---|---|
> | **L1 锚点** | 写进每会话必读处 | ✅ 项目 `CLAUDE.md` 里有 |
> | **L2 触发** | 时机到了会被想起来 | ❌ **无** —— 派子 Agent 那一刻没有任何提醒 |
> | **L3 硬门** | 漏了会红 | ❌ **无** |
>
> **它本身就是本篇批评的「只有文字」。**
> 补 L3 的做法(已落地):**`SubagentStart` 事件直接注入纪律**(见 §1.2 与 `A3-R8`),
> 不再依赖主 Agent 记得。**任务描述仍要写业务约束** —— 两者解决的不是同一件事。

---

### `A3-R2` · 优先把约束**下沉到仓库层**(一次投入,对所有 Agent 永久生效)

**规则**:能写成 hook / CI / 测试的,**不要只写在任务描述里** ——
**任务描述是"这一单"的,hook 是"每一单"的。**

**反例(实证)**:见 §3 判断表 —— 会话级机制(锚点、SessionStart、Stop)对子 Agent **无效或不触发**;
只有**仓库级**那三行(仓库级 hook / CI / 代码与文档注释)是真的有效。

**正例(怎么做到)**:每加一条约束,先问「它能不能变成一条**机器可判**的痕迹?」
能 → 写成 hook 或 CI 检查(判据与强度标注见 `A2-R5`);不能 → 至少写进**仓库内的**文档/注释(`A3-R7`)。

---

### `A3-R3` · 要求它交【**机器可读的交付物**】,而不是口头保证 —— **但优先自动抽取,不要靠自述**

**规则**:把"证明你做了功课"从**请求**变成**强制**:产出物强制携带机器可校验的字段
(`source` 依据 / `check` 怎么验的 / `test` 对应测试;**`source` 为空 → 直接拒绝**)。
**但更进一步**:**能自动采集的,就不要让它自述** —— 一份"交付物"如果**需要 Agent 主动填写**才算数,
它迟早会退化成八股;如果**能从既有的机器痕迹里抽取**,才是硬的。

**反例(实例)**:见 §2 —— 对空上下文子 Agent,「让它改代码 + 提交前先交一份 trace(读了哪些文件、
调了哪些 Skill、依据哪条规则)」看似有效,**但它需要 Agent 主动填写**;
一旦变成必填项,就会变成**照着格式填**。

**正例(怎么做到)**:子 Agent 的 skill 调用**由 hook 从它的 transcript 自动抽取**
(示例,本仓实现:`skill-trace.sh`,扫 `<session_dir>/subagents/*.jsonl`),
**不需要它多写一个字**;纪律注入同理 —— **由 hook 注入、由 transcript 断言到达**。
⇒ **判断标准**:自发填写的 ⇒ 迟早八股;自动抽取的 ⇒ 才是硬的。(同源规则:`A2-R10`。)

---

### `A3-R4` · 子 Agent 改完,主 Agent 必须**独立复核**

**规则**:跑测试、看 diff —— **不要采信它的自述**。"它说通过了"不是证据;"我跑过、我看了 diff"才是。

**反例(实例)**:见 §2 的取证方式 —— 本篇全部结论都来自**对 transcript 的工具调用统计**;
反过来说,**自述在实测中被证明不可采信**(同一个 Agent 既可能"以为"自己合规,也可能漏做)。

**正例(怎么做到)**:主 Agent 收尾时**重跑一遍测试** + `git diff` 过一遍改动范围
(顺手确认它没有越界改别的文件、没有顺手绕过门禁)。

---

### `A3-R5` · 多阶段长任务用**状态机交接**

**规则**:委派"多阶段长任务"时,把阶段计划写成**机器可读的阶段文件**(示例:`stages.json`),
让它每完成一阶段就**显式通过一次阶段门**(**产出物必须真实存在才算过**)。
好处有三:① 它**不能跳步**(前置未通过就直接拒绝);② 中途被打断可 `resume`
**从第一个断点续跑**;③ 产出物**事后被删/被改坏时,resume 会退回该阶段** —— 不会"假装已完成"。

**反例(实例)**:**不要**用"最高的已通过阶段"作为续跑起点 —— 那样**删掉产出物之后,它会假装已完成**。
(该判据正是实现时被纠正的一条。)

**正例(怎么做到)**:参考实现(示例,本仓实现:`tools/stage_gate.py`)——
阶段门前**校验前置阶段 passed 且产出物现在仍在**。

### `A3-R6` · 用**判断表**判断"这条纪律对子 Agent 有没有效";只在会话里存在的 → 对子 Agent 不存在

**规则**:一条纪律落地前,先按 §3 的判断表定位它写在哪一层;若**只在会话里存在**
(锚点文字、会话级 hook),则它对子 Agent **等于不存在** ⇒ 必须**下沉到仓库层**。

**反例(实证)**:见 §2 —— 同一个子 Agent:
**锚点在场(没读/不照做)、会话级 hook 全部未触发**;只有仓库级硬门生效。

**正例(怎么做到)**:① 逐机制的"有效/无效"清单见 **`A4-R11`** 与 `A4` 篇 §5;
② 判断表里每一行都有对应的"要怎么补"(锚点 → 补注入;会话级 hook → 改成仓库级 hook / CI)。

### `A3-R7` · 写 hook 时**注释要当成文档写** —— hook 是锚点的替代品

**规则**:hook 源码同时是**给 Agent 阅读的文档**。注释里要写清 **"为什么有这道门、判据是什么、绕过会怎样"**,
因为**真的会有 Agent 逐行读它**,并据此决定自己的行为。

**反例(实证)**:见 §3 的 ⭐ 小节 —— **2/2 两个 Agent 在动手写码之前主动 `cat` 了本地门禁源码**,
并据此**主动先写测试**;反面对照:两者**都没读 `CLAUDE.md`**。
⇒ 起作用的是 hook 源码,**不是锚点**。

**正例(怎么做到)**:脚本头注释写全"这道门为什么存在 / 什么情况该拦 / 豁免怎么走、要写什么理由";
把该写的规矩写进注释,而不是只写进锚点文件。

---

### `A3-R8` · 注入兜的是「**纪律**」;**任务描述仍必须携带「业务约束」**

**规则**:纪律注入(把最小纪律集直接注入子 Agent 上下文)解决的是**通用纪律到达**;
**它兜不住"这次要做什么、边界在哪"** ⇒ **业务上下文必须由主 Agent 写进任务描述**。

**反例(实例)**:把注入当成"任务描述可以少写"的理由 —— 注入块里**没有**"本次要改哪个模块、
不许碰哪些文件、验收标准是什么"这类信息,只能来自任务描述。

**正例(怎么做到)**:两边各写各的:任务描述 = **业务约束**(`A3-R1` 的最小集);
注入 hook = **通用纪律**(改码先写测试 / 称完成前验证 / 提交前留痕)。

---

### `A3-R9` · 判断子 Agent 的行为,**只能查它的 transcript**;且要区分「**拿到**」与「**照做**」

**规则**:① **取证查 transcript**,别问它(`A3-R10` 是"到达性"探针,这里说的是**行为取证**);
② **它没 `Read` 某个文件 ≠ 它没拿到那个文件的内容** —— 锚点全文可能就在它的上下文顶部。
⇒ 由"它没读"推出"它拿不到",是**已被证伪**的因果跳跃(见 §1.1)。

**反例(实例)**:见 §1.1 —— 连续几轮的结论「Skill 调用 0 次」「它没有 Read `CLAUDE.md`」
被**错误地**读成「拿不到」,直到只读探针让它**逐字引用**锚点全文才推翻。
**这是同类错误的第三次** ⇒ 规则见 `A2-R9`(下"做不到"的结论前先验证一次)。

**正例(怎么做到)**:报告里把两件事分开写 —— **"它有没有看到"**(上下文证据:注入块 / 逐字引用探针)
与 **"它照不照做"**(行为证据:transcript 里的工具调用)。
**结论只能落在第二项上**:锚点在 ≠ 会照做。

### `A3-R10` · 验证「约束是否真的**到达**」:下一条**只出现在任务描述里**的探针

**规则**:在任务描述里塞一条**只出现在任务里**的标记要求(示例:"提交信息加 `[sub-agent]`"),
再看它照不照做 —— **这是"约束到达性"的探针**:它照做了 ⇒ 通道通;没照做 ⇒ 该通道没送达。

**反例(实例)**:只凭"我把要求写进去了"就假定送达 —— 见 §1.1/§2 的教训:
**写进去 ≠ 送达 ≠ 照做**,每一步都要各自取证。

**正例(怎么做到)**:探针标记要在**仓库里不存在**(否则无法区分它从哪儿看来的);
事后在它的 transcript / 提交信息里**查这个标记**。

### `A3-R11` · 「**下沉是否有效**」有**三种**结果,不是两种

**规则**:判断一条约束下沉(去掉任务描述里的说明、只靠 hook)后是否有效,别只分"拦住/没拦住":

| 结果 | 观察 | 强度 |
|---|---|---|
| ① **被拦住** | 提交被拒,Agent 被迫改正 | 强 —— 2/2 实证 |
| ② **事先合规,门不响** ⭐ | Agent 在动手前**主动读了 hook 源码**并据此合规 | **比 ① 更强** —— 门禁作为**可读结构**事先塑造了行为(2/2) |
| ③ **没拦住** | 门失效 / 被绕过 | 失效 |

**反例(实例)**:只预设"拦住 / 没拦住"二元 ⇒ 会把**②误判成③**(门没响 ⇒ "门没用")。
实际观测里,**② 是常态**(两个 Agent 都提前读了门禁源码并合规)。

**正例(怎么做到)**:② 的存在还有一个重要推论:**当 Agent 会主动侦察时,
「拦截力」这个指标天然难以测到** —— 想复测拦截力,必须让**"侦察"本身失效**,
而不是**"把文件藏起来"**(实测:藏在仓库外的门禁被两个 Agent 提前找到并读了)。
⇒ 详见 `A4-R5` / `A4-R7`。

### `A3-R12` · 「**注入是否真的到达**」必须**可自动化验证**

**规则**:注入块带一个**版本签名**,事后 `grep` 子 Agent 的 transcript
(`<session_dir>/subagents/agent-*.jsonl`)。**判据:有子 Agent 却一份都不含签名 → 结构失效。**

**反例(实例)**:注入 hook 写完就假定"它一定到达了" —— 而 hook **静默失效**是真实存在的一类故障
(示例:输出非法 JSON 的 hook 会**静默失效**;见 `A2` 篇的实现坑),
**没有断言就等于没有这条结构**。

**正例(怎么做到)**:示例(本仓实现):`tools/check_subagent_injection.py`,
由 Stop 哨兵在失效时出声;签名随注入块一起进上下文,断言只看**客观 grep**。

## 5. 给 Kit / 平台维护者

这不是单点坑,是**结构性的**:

1. **scaffold 的 `CLAUDE.md` 纪律段,对子 Agent 无效** —— 必须在文档里**显式说明**这一点,
   并把「委派时携带约束」写成一条**锚点纪律**(否则主 Agent 也不知道自己该做这件事)。
2. **能下沉到仓库级的,一律下沉**:hook / CI / 测试 > 锚点文字。
3. **提供"trace / 交付物清单"的模板**,让委派有标准可依,而不是每次临时想。

## 6. 适用场景与不适用场景

**适用**:

- 你要**派子 Agent**(含并行委派)—— 先过 `A3-R1` / `A3-R2`;
- 你要**制定一条约束,并希望它对子 Agent 也有效** —— 过 `A3-R6` + `A4-R11`;
- 你要**交长任务**(多阶段)—— 过 `A3-R5`;
- 你要**核实子 Agent 有没有照做**(或核实"注入有没有到达")—— 过 `A3-R9`…`A3-R12`;
- 你是 **Kit / 平台维护者**,要把这些约束做成 scaffold 的一部分 —— 见 §5。

**不适用 / 注意**:

- **主会话自身的纪律落地**(写进每会话必读处 / 加触发 / 加硬门)**不在本篇** —— 见 `A1` 篇;
- **门禁 / hook 自身的生命周期**(会腐烂、会被发现、会锚错地方、哪些机制对子 Agent 真有效)
  **不在本篇** —— 见 `A4` 篇(逐机制清单在 `A4-R11` 与 `A4` 篇 §5);
- **不要用"提醒它记得遵守"来替代携带约束** —— 那正是本篇证伪的做法;
- **注入不能替代业务上下文**(`A3-R8`);
- 一次性、无风险的探索型子任务**不必**走完整委派清单(但**其结论不得直接当证据**,见 `A1` 篇)。

## 8. 怎么验证它被落地

| 规则 | 怎么验证(通用判据) |
|---|---|
| `A3-R1` | 抽查最近几次派发记录:任务描述里**有没有**「约束」段?没有 ⇒ 该次等于无纪律委派 |
| `A3-R2` | 把任务描述里的约束**全部删掉**,只靠仓库层 → 门禁**仍**拦住 ⇒ 下沉成功(三种结果见 `A3-R11`) |
| `A3-R3` | 交付物里**需要 Agent 主动填写**的字段有几个?能改成"从既有痕迹抽取"吗?—— 填的越多,越容易八股 |
| `A3-R4` | 主 Agent 的收尾记录里,有没有**它自己重跑测试 / 看 diff** 的痕迹(而不是转述子 Agent 的话) |
| `A3-R5` | 中途打断一次任务再 `resume`:是否**从第一个断点**续跑?删掉某阶段产出物后 `resume`:是否**退回该阶段**? |
| `A3-R6` | 逐条问"这条纪律写在哪一层";答"只在会话里"的条数 ⇒ 就是它对子 Agent 失效的条数 |
| `A3-R7` | hook 脚本的注释里,是否写了"为什么有这道门 / 绕过会怎样"?写成只有代码没有解释 ⇒ 未落地 |
| `A3-R8` | 注入上线后,任务描述里是否**仍然**写了业务约束(改哪个模块 / 不许碰什么 / 验收标准) |
| `A3-R9` | 结论里有没有出现**从"它没读"推出"它拿不到"**?有 ⇒ 违反了本条(见 §1.1 的更正) |
| `A3-R10` | 最近一次委派里有没有**只出现在任务描述里的探针标记**?事后在它的 transcript / 提交信息里查得到吗? |
| `A3-R11` | 记录"门没响"的原因时,**是否区分了 ②(事先合规)与 ③(失效)**?只写"没拦住" ⇒ 判据不完整 |
| `A3-R12` | 最近一轮有子 Agent 的工作里,grep 它的 transcript:**有没有一份含注入签名**?一份都没有 ⇒ 结构失效 |

**反检验(最有说服力)**:任取一条,问 ——
**"如果这条被违反了,有没有任何东西会变红或出声?"** 答"没有" ⇒ 它还没落地(回到 `A3-R2` 下沉)。
