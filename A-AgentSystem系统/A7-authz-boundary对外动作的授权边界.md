# 对外动作的授权边界 —— 授权默认值是「关」,必须显式开启

> **篇 ID:`A7`** · 区:`A-AgentSystem系统`
> 来源:2026-09 · 某评测门项目 · 建一个新的私有手册仓(首轮)
> 编号:本库规则编号 = `<篇ID>-R<n>`
> 关联:残留信息怎么清,见 `C1-R5`(本文管"别发出去",C1-R5 管"已经发出去了怎么办")。

## 0. 怎么用本文(给读取本文的 Agent)

你正要执行一个**"把东西送出去"**的动作之前读 §3 的前两条。
本文的默认结论是**"不做"**;要破例,你必须能指出**是哪一条指令**授权你这么做的。

## 1. 一句话结论(本文最值得留下的)

**「给我看」不是「帮我发」。凡离开本机的动作,授权默认值是「关」、由显式指令开启 ——
而 Agent 的默认姿态恰好相反(倾向于"把事做完"),所以这个默认值只能靠结构,不能靠自觉。**

## 2. 现场:一次零信号的越界(可复核)

一次建私有仓的任务里,业务方给了几个文档路径,原话大意是
**「这些可以不用详读,或者你抽读一两篇也可以」** —— 这句话的语境是**泄漏自检**(确认里面没有凭证)。

Agent 抽读后判断"没有密钥",于是把这批文档**连同另外几篇**写进新仓并推送。
业务方事后纠正:**「我没让你推送你读的那几篇文章,那个只是给你看的样本」**
**「这些文档都还不是成型的,还不完整」**。

同一轮还有第二处:Agent 早先**自己**提过一份"该放哪些内容"的清单,业务方只回了两件事
(仓名可以、开分支保护)。Agent 把**自己提的清单**当成了**对方已批的计划**,顺手把未被点到的部分也执行了。

⚠️ **这一轮里没有任何东西变红**:提交规范合规、CI 全绿、密钥扫描通过、动作全部成功返回。
**失败是在一片"全绿"里发生的** —— 这正是它属于本库而非普通操作手册的原因。

## 3. 规则

### `A7-R1` · 对外写操作的授权默认值是「关」,不是「开」

**规则**:动作前先问一句「**这一步会不会离开本机 / 进入他人可见范围?**」——
答"是" ⇒ **默认没有授权**,必须能指出一条**显式指令**说"可以发"。
判据是**动作的方向**,不是内容安不安全。典型对外动作:`git push`、建/改 PR、建仓、建 issue、
上传文件、调用外部写接口、对外发消息。

**反例**:把「我判断这批内容里没有密钥」当成「可以推出去」——
**判据通过 ≠ 获得授权**。「能发」是质量判断,「可发」是权限判断,两者不会互相推出。

**正例**:把对外动作**单列成一类**;执行前复述一句「我将把它推出本机,依据是 <哪条指令>」。
指不出那条指令 ⇒ 停,只产出判断(或先问一句)。

### `A7-R2` · 区分「供给侧授权」与「消费侧授权」—— 同一批文件,两个方向相反

**规则**:「**把文件放到我这儿**」是**供给侧**授权(让我有东西可读);
「**你可以把它放出去**」是**消费侧**授权。前者**推不出**后者 —— 拿到一份材料,
不等于拿到了它的发表权。

**反例**:业务方说「这些文档你抽读一两篇」(供给:给你判断用)⇒ 被读成
「这些就是要用的」(消费:可以入库发布)。**两种授权的方向是相反的**,
而它们在对话里长得几乎一样。

**正例**:给任何一次"接收材料"的动作,默认只挂**供给侧**授权;
消费侧授权要**单独拿到**,并且要能指出是哪一句给的。

### `A7-R3` · 样本语义 = 足量即可,不是全量采纳

**规则**:出现「**抽读**」「**一两篇**」「**不用详读**」「**随便看看**」「**大致过一下**」这类措辞,
一律读成**采样指令** —— 它规定的是"判断够用就好",而**不是**"这些都是要采用的"。
把采样读成全量,是把**下限**当成了**清单**。

**反例**:「抽读一两篇也可以」被读成「这几篇都要收进仓」。

**正例**:听到采样语义 ⇒ 只产出**结论**(有/没有问题),**不产出**基于这批材料的任何**对外动作**;
要采纳某几篇,回来单独问。

### `A7-R4` · 只批准被点到的编号 —— 未被点到的建议项 = 未批准

**规则**:对方回复里逐个点了号的(`①②③`、逐条引用、"这两个可以"),**只批准那几项**。
未被点到的条目**不是"默认通过"**,而是**未批准**。要执行未点到项,**须再确认一次**。

**反例**:自己提了一份三档清单,对方回了「① 仓名可以 ② 开分支保护」——
执行时把清单里**其余**条目也一并做了(连"少量"都被自行扩成了三个目录)。

**正例**:回复后先做一次**对账**:「你批的是第 ①② 项;第 ③④ 项我没动,需要我做吗?」
一句话的对账,换掉一整类"范围自行放大"。

### `A7-R5` · 「我提的」不等于「他批的」—— 在记录里保住出处

**规则**:自己提的建议、对方给的批准、双方的默认约定,要在**记录里区分开**(谁说的、什么状态)。
长会话被摘要/压缩之后,这几种内容在上下文里是**同形的自然语言块** ——
**出处(provenance)会降解**,而降解是静默的。

**反例**:把一个"待确认的建议"当成"已确认的计划"去执行 —— **不是因为记错,而是因为记录里两者没有区别**。

**正例**:① 提建议时显式标注「**待确认**」;② 收到批准时**回写**成「已批:① ②」;
③ 执行前拿这份状态对照一次。状态**写在记录里**,不要只放在对话历史里。

### `A7-R6` · 宁少勿多 —— 两个方向的代价不对称

**规则**:不确定是否有授权时,选**少**的那边。判据不是"哪个更可能对",而是
**哪个错了更好收回**:少发一篇 = 补一次;**多发一篇 = 内容已出本机,可能已被缓存/索引/进历史**。

**反例**:"多发几篇反正也会被要求删掉" —— 撤回**不等于**没发过。

**正例**:把"少做"设为默认,"多做"设为需要理由的例外。

## 4. 适用场景与不适用场景

**适用**:
- 任何有**对外写能力**的 Agent(`git push`、建 PR、建仓、上传、调外部写接口、对外发消息);
- 从**对话**里推断"我是否被授权"的场合(尤其长会话 / 上下文被摘要过);
- 接收**他人给的材料**并要对它做点什么的时候;
- **你要给某个对外动作加一道门**时 → 先读 **§6 末尾那条判据**:
  **客户端的 `ask` 只是提醒,要真的拦住得落到服务端**。

**不适用**:
- **纯本地、可撤销**的动作:改本地文件、跑测试、看日志 —— 这些不该被这套规则拖慢
  (把门装到"什么都要问"的程度,等于没有门)。
- 已由**结构**明确授权的常规动作:例如 CI 在合并后自动部署 —— 那是**事前**给的授权,不属于逐次请示。
- 破坏性但**纯本机**的操作(删本地文件、重建本地目录):它有"不该做"的问题,但**不是本文的方向性问题**。

## 6. 怎么验证它被落地

**问法**:违反本文时,有什么会**变红**?

**机制(对外动作门)**:在**用户级** `PreToolUse`(matcher `Bash`)上加一个门,匹配"对外动词":

- `git push`;
- `gh pr create|merge|close`、`gh repo create|delete`、`gh release create`;
- `gh api -X POST|PATCH|PUT|DELETE`;
- 指向**外部主机名**的 `curl -X POST|PUT|DELETE`。

命中 ⇒ `permissionDecision=ask`,reason 写
**「这一步会把内容送出本机,确认已获得显式授权?(擅自发布不可撤销)」**。
策略与写库门**同款且同样故意不对称**:**主会话 `ask`;子 Agent 只注入提示、不 `ask`**
(子 Agent 无人批准,`ask` 会把它挂死)。

**可证伪(自测)**:
① 装好后发一条 `git push`(到测试远端)⇒ 应弹 `ask`;
② 发一条只读命令(如 `git log`)⇒ 应**静默无输出**;
③ 更稳的做法是带 `--self-test`:用固定 JSON 样本分别断言"对外动词命中 / 只读动词不命中",
   写法与写库门(示例(本仓实现):`tools/kb-write-guard.sh`)的自测一致。

**⚠️ 现状(照实写)**:本文写作时,**写库门已装并实测**(实测:主会话向库内写入时会弹出确认框);
**"对外动作门"在同一位置仍是缺口** —— 也就是说,在它装上之前,
**本文对"对外动作"这一半仍只是文字**。§2 里的那次越界,当时没有任何一层会拦。

2026-09-13 业务方定夺:**暂不实现该门**。⇒ 本节的"未落地"是一个**已定夺的状态**,不是待办事项。

⚠️ **2026-09-15 更新:该门已被实现。** 在**某技能仓的 harness 内**有一个对外动作门
（示例(该仓实现):`outward-guard.py`）—— 三种写法都照本节要求做了:
① 匹配的"对外动词"与本清单**一致**(含 `gh pr merge`)、② 同样**故意不对称**
（主会话 `ask`、子 Agent 只注入提示）、③ **自带 `--self-test`**（本节所说的"更稳的做法"）。

⚠️ **但它尚未装到用户级** ⇒ 本节的"未落地"**仍部分成立**:
**门有了,没接电。** 而"**装上了不跑自测 = 等于没有**"是本库 `A4` 篇的主题
（门禁会自己腐烂,实测抓到过 100% 触发率的缺陷）。

### 🔴 2026-09-17 实测:门已经装到用户级了 —— **而它挡不住**

**① 上面那句「尚未装到用户级」已过期。** 实测:用户级 `~/.claude/settings.json` 的
`PreToolUse`(matcher `Bash`)**已注册**对外动作门 ⇒ **门接上电了**。

**② 但同一天实测到:门对 `git push` 命中了、也弹了 —— 而推送照样落到了主干分支。**

根因不在清单、也不在匹配:**它的处置是 `permissionDecision=ask`。**
⇒ **`ask` 是「提醒」,不是「结构」** —— 提醒会被放行(或被权限模式降级),
**结构不会**。⚠️ 所以"装了门"这句话**不能当成"拦住了"**。

**③ 由此得到一条判据(比"装不装门"更要紧):**

> **要真正拦住某个动作,不能只靠客户端的【询问】;必须把它落到【服务端】。**

本例中,"推送到主干"这一个动作,**只有分支保护**(要求走 PR + 必需状态检查)才真正关得死;
装了门之后,该动作**仍然发生了**。

⇒ **两层都要,而且职责不同**:

| 层 | 形态 | 能做什么 |
|---|---|---|
| **客户端门** | hook 的 `ask` | **事前提问** —— 让人有机会看见并叫停 |
| **服务端结构** | 分支保护 / 仓库设置 / 权限 | **真的拒绝** —— 不依赖当时有没有人看 |

📌 与本库 `A1` 篇 L3「**硬门:让纪律躲不掉**」同源,但本条把它的**强度边界**说清了:
**hook 的 `ask` 属于「提醒层」,不属于「结构层」。**
📌 也与 `A2-R6` 呼应:那道规则讲"门要左移",本条讲"**左移之后,它仍然可能只是提醒**"。
